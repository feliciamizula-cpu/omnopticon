ArgusGrid Wrapper: 3 Approaches

How should the wrapper expose MudBlazor DataGrid to callers?

A

Model-Driven Columns (Thin Facade)

Keep a GridColumn<T> model. The wrapper translates it to MudDataGrid internally. Callers don't write any MudBlazor markup.

Pros

  • Familiar — same pattern as current code
  • Callers need zero MudBlazor knowledge
  • Consistent usage across all pages

Cons

  • Custom cell renderers need model extensions
  • Every new MudDataGrid feature requires wrapper updates
  • Leaky abstraction over time
Example usage 
<ArgusGrid TItem="ProgramItem"
           Items="_programs"
           Columns="_programColumns"
           OnRowClick="SelectProgram"
           ContextMenuItems="_programMenu" />

// Columns defined in code-behind:
new GridColumn<ProgramItem> {
    Header = "Name",
    Value = p => p.Name,
    Width = "1fr"
}
B

RenderFragment Columns ✦ Recommended

ArgusGrid accepts MudBlazor column components as child content. The wrapper adds: theme, context menus, empty state, row click. Callers write standard MudDataGrid column markup.

Pros

  • Full MudDataGrid power (custom renderers, grouping, footers)
  • Wrapper stays thin and stable
  • Future MudDataGrid features work automatically
  • No model translation layer to maintain

Cons

  • Callers need basic MudBlazor column knowledge
  • More verbose in markup than model approach
Example usage 
<ArgusGrid TItem="ProgramItem"
           Items="_programs"
           OnRowClick="SelectProgram"
           ContextMenuItems="_programMenu">
  <PropertyColumn Property="p => p.Name" Title="Name" />
  <PropertyColumn Property="p => p.ScopeCount" Title="Scopes" />
  <TemplateColumn Title="Status">
    <CellTemplate>...custom render...</CellTemplate>
  </TemplateColumn>
</ArgusGrid>
C

Hybrid — Model + Slot

Provide both: simple Columns parameter for the common case, plus a ColumnsTemplate RenderFragment slot for complex custom columns.

Pros

  • Best of both — simple when possible, powerful when needed
  • Gradual migration path

Cons

  • Two patterns for callers to learn
  • Larger, more complex wrapper
  • Model translation AND RenderFragment paths both need maintenance
Example usage 
// Simple case (model-driven):
<ArgusGrid TItem="AssetItem" Items="_assets"
           Columns="_assetColumns" />

// Complex case (template slot):
<ArgusGrid TItem="AssetItem" Items="_assets">
  <ColumnsTemplate>
    <TemplateColumn ...>...</TemplateColumn>
  </ColumnsTemplate>
</ArgusGrid>
