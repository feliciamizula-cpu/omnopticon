## Findings

### Critical

1. **review-agents.sh:174-188 - Unchecked PIPESTATUS after opencode**
   ```bash
   printf '%s\n' "$prompt" | "$OPENCODE_BIN" run --dir "$WORK_DIR" 2>&1 | while IFS= read -r line; do
       log "[$reviewer] $line"
   done
   exit_code=${PIPESTATUS[1]}
   ```
   The pipe to `while` introduces an additional subshell. `PIPESTATUS[1]` captures the opencode exit code correctly, but if the `while` loop itself fails (e.g., due to a signal), `exit_code` could reflect the wrong process. Use `set -o pipefail` and capture `${PIPESTATUS[0]}` directly after the cat/pipe.

2. **tools/agent-coord.sh:361-429 - reconcile_state() holds lock for entire iteration**
   The `acquire_lock` at line 362 is held while looping through all agents and making multiple state writes. If any `agent_write_state` or `write_state` call takes significant time or blocks, all other concurrent `agent-coord.sh` invocations (e.g., checkpoint calls from running agents) will be blocked. Consider releasing the lock between agent iterations or using shorter critical sections.

3. **tools/auto-run-agents.sh:507-527 - Heartbeat subprocess not tracked for cleanup**
   ```bash
   (
       while kill -0 "$runtime_pid" 2>/dev/null; do
           sleep 45
           ...
       done
   ) &
   heartbeat_pid=$!
   ```
   The heartbeat subprocess is started after the agent process. If `spawn_agent` exits prematurely (e.g., opencode dies instantly), `heartbeat_pid` is still captured, but the heartbeat subshell may race with the parent's `kill "$heartbeat_pid"`. Race condition: the subshell may already be gone when `kill` is called, or a new heartbeat for a subsequent agent could reuse the same PID. Use a process group (`set -o monitor` + `kill -PID` of the process group) or store PID in a file.

### High

4. **tools/agent-coord.sh:414-420 - Task requeued with stale context after crash detection**
   When `reconcile_state()` detects a crashed agent, it requeues the task with `.recoveryContext = (if $context == "" then null else $context end)`. The context from the crashed agent may be incomplete or corrupted if the agent was interrupted mid-write. No validation that the context is valid JSON or non-circular.

5. **src/Services/Argus.ScanOrchestratorService/Program.cs:165-170 - HTTP client created per-asset in loop without disposal**
   ```csharp
   foreach (var asset in assetsResult.Items.Take(10))
   {
       using var request = new CreateReconTaskRequest(...);
       using var taskResponse = await taskClient.PostAsJsonAsync(...);
   }
   ```
   The `HttpClient` is reused across all assets (good), but each iteration uses `using` on the response, which is fine. However, the `HttpClient` itself is never disposed on errors in the loop. If `ProcessScheduledScanAsync` throws mid-loop, the `HttpClient` leaks until `ProcessScheduledScanAsync` is called again.

6. **tools/dashboard.sh:170-184 - get_critical_alerts() reports "BUILD CHECK PENDING" as critical**
   ```bash
   case "$build_status" in
       FAILED)
           alerts="${alerts}BUILD FAILED"
           ;;
       CHECKING)
           alerts="${alerts}BUILD CHECK PENDING"
           ;;
   esac
   ```
   "CHECKING" is treated as a critical alert and shown in the red warning banner with `⚠ CRITICAL ALERTS:`. A pending build check is not a critical condition. This could cause alert fatigue and mask real build failures.

7. **src/Services/Argus.AssetService/Program.cs:728-740 - ComputeStalenessScore uses hardcoded intervals without validation**
   `ExpectedScanIntervals` and `MaxStalenessInterval` are hardcoded static dictionaries. If an `AssetType` is added to the enum but not to `ExpectedScanIntervals`, it silently defaults to 7 days. A type-unsafe `GetValueOrDefault` means a typo in an asset type string would also silently use the default. Consider logging a warning for unmapped types.

8. **src/Contracts/Argus.Contracts/Tasks/TaskContracts.cs - WorkerPriority enum missing explicit values**
   The `WorkerPriority` enum used in `CreateReconTaskRequest` has implicit integer values (0, 1, 2). The ordering `High=0, Normal=1, Low=2` is relied upon in `EfTaskStore` for SQL `>=` comparison (`task.Priority >= request.MinimumPriority`). If enum members are reordered during future development, the SQL logic silently breaks. Use explicit values.

### Medium

9. **tools/agent-coord.sh:247-250 - take_task() uses `.status // "active"` which masks "inactive"**
   ```bash
   .status = (.status // "active") |
   .workStatus = "working" |
   ```
   If an agent is truly inactive (e.g., disabled), this silently overrides the inactive status to "active". The intent appears to be defensive handling of null, but it should probably reject or warn when taking a task for an inactive agent.

10. **tools/auto-run-agents.sh:653-654 - git_pull || true masks all errors**
    ```bash
    git_pull || true
    ```
    If `git_pull` fails due to network, auth, or merge conflicts, the supervisor continues silently. Operational visibility is lost. At minimum, log a warning when `git_pull` fails.

11. **tools/agent-coord.sh:680-684 - doctor_agents() output to stdout, not parseable machine output**
    `doctor_agents()` emits free-text warnings like `"WARN $agent_id: missing or empty local state file"`. This cannot be consumed programmatically for alerting. Consider exiting with a non-zero code when issues are found, or outputting JSON.

12. **review-agents.sh:137-150 - spawn_reviewer() uses string-based SHA-1 for batch_id**
    ```bash
    batch_id="$(batch_id_for_commits "$commits")"
    ```
    The batch ID is a 12-char SHA-1 prefix of the concatenated commit hashes and messages. This is non-deterministic if the commits change order (though `git log --reverse` provides a stable order). If two reviewers compute different batch IDs for the same set of commits (e.g., due to race condition in `commit_batch()`), they would never mark the batch as complete. Use a canonical serialization (sorted commit hashes only) for the batch ID.

13. **tools/agent-coord.sh - reconcile_state() and checkpoint_agent() can race**
    Both functions acquire the same lock but `write_state` itself is inside the locked section while also calling `agent_write_state` for each agent. If an agent's `checkpoint_agent` runs concurrently during reconciliation, they could be writing to the same state files simultaneously. The per-agent lock in `agent_write_state` doesn't protect against concurrent `write_state` calls.

14. **src/Services/Argus.ScanOrchestratorService/Program.cs:152-156 - ScheduledScanBackgroundService processes scans sequentially**
    ```csharp
    foreach (var scheduled in dueScans)
    {
        try { await ProcessScheduledScanAsync(...); }
    }
    ```
    Scans are processed one at a time with `await`. If one scan's `ProcessScheduledScanAsync` is slow (network-bound), other due scans are delayed up to 1 minute (the loop interval). Consider `Task.WhenAll` with a bounded degree of parallelism.

15. **tools/review-agents.sh:61-70 - read_reviewer_state() uses jq but no error handling if jq fails**

## Open Questions

1. **AssetDto.StalenessScore** is computed server-side at query time (`ComputeStalenessScore()`) but not persisted. This means identical queries at different times return different staleness scores for the same asset. Is this intentional for real-time staleness, or should it be precomputed and stored on the asset record?

2. The `reconcile_state()` function in agent-coord.sh requeues tasks that were "in_progress" but whose assignee is not currently working them. What is the expected behavior when multiple agents race to reclaim the same requeued task? Does the task board locking prevent double-assignment?

3. The `WorkerPriority` enum has three values (high/normal/low). In `EfTaskStore.LeaseTaskAsync`, the SQL uses `task.Priority >= request.MinimumPriority` with `(int)request.MinimumPriority`. If a worker requests `WorkerPriority.Normal`, it would receive tasks with priority >= Normal (i.e., Normal and High). Is this the intended semantics, or should the comparison be equality-based?

## Residual Risk

The batch includes significant infrastructure changes to the agent supervisor loop, state reconciliation, and dashboard. The riskiest changes are:

- The `reconcile_state()` function which rewrites task state based on agent runtime status — a bug here could reassign tasks incorrectly or lose work.

- The new dead-letter admin endpoints which expose message replay functionality without authentication.
- The `git_pull || true` pattern which will silently fail on network/auth issues.

The bug fixes (Bug #13, #14, #15) and enhancements (#4, #5) are self-contained and low risk. The task completion commits are operational tooling changes.
