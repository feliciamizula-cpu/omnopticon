### 2. Inconsistent Retry Logic — Requeue Happens After Max Retires

**Commit:** `cc93e58`
**File:** `src/BuildingBlocks/Argus.BuildingBlocks.EventBus/RabbitMqConsumerService.cs:94-104`

```csharp
if (retryCount >= _maxRetries)
{
    _logger.LogWarning("Message {DeliveryTag} exceeded max retries, moving to DLQ", ea.DeliveryTag);
    await _channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false, stoppingToken);
}
else
{
    await _channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: true, stoppingToken);
}
```

When `retryCount >= _maxRetries` (i.e., 3), the message is Nacked with `requeue: false`, which routes to DLQ as intended. However, when `retryCount < _maxRetries`, it Nacks with `requeue: true`. RabbitMQ will redeliver the same message, which re-enters `ReceivedAsync`, increments the death count, and Nacks again on failure. This is a valid retry pattern, but the implementation conflates requeue with retry—the message will be reprocessed entirely, not continued.

**Risk:** Medium. The behavior is functional but not idempotent-safe. Messages that partially succeed then fail will re-execute their full logic.

### 9. Shell Script Diff Verbosity — Temporary File Pattern

