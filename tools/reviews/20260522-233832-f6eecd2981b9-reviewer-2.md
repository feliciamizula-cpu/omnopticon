## Findings

### HIGH PRIORITY

1. **review-agents.sh: Potential infinite loop under branch condition (lines 243-249)**
   - In `spawn_reviewer()`, the bash process reads prompt via `printf '%s\n' "$prompt" | "$OPENCODE_BIN" run --dir "$WORK_DIR" 2>&1 | while IFS= read -r line`. The PIPESTATUS check `exit_code=${PIPESTATUS[1]}` is unreliable when the while loop may consume stdin. If opencode exits before reading all input, the while loop continues waiting on stdin forever. The background subshell `(&)` ensures supervisor loop continues but the spawned reviewer could hang.
   - File: `tools/review-agents.sh:243-249`
   - Risk: Reviewer agent hangs; supervisor moves on but orphaned process may consume resources.

2. **auto-run-agents.sh: Supervisor no longer resumes crashed/stalled agents (lines 576-588)**
   - In `5ebef78c367084de7854520c020a8121c58a37df`, the resume logic for crashed/stalled agents was removed from `run_agent_if_needed()`. Previously lines 601-611 would respawn an agent onto its current task if the runtime was crashed/stalled/working. This behavior was intentionally removed; now `run_agent_if_needed()` only assigns new work to idle agents. Crash recovery now depends entirely on the `reconcile_task_board()` periodic call and the reconcile logic in `agent-coord.sh:reconcile_state()`. This is a behavioral regression if agents were previously self-recovering.
   - File: `tools/auto-run-agents.sh:576-588`
   - Risk: If reconcile interval is too large, tasks can be stuck on crashed agents. Monitor `AGENT_STALE_TIMEOUT` and `RECONCILE_INTERVAL` carefully.

3. **auto-run-agents.sh: PID tracking mismatch between supervisor and agent (lines 505-517)**
   - In `spawn_agent()`, `exit_code=${PIPESTATUS[1]}` relies on opencode being in pipe position [1]. However, the pipeline is `cat "$prompt_file" | "$OPENCODE_BIN" run --dir "$WORK_DIR" 2>&1 | while IFS= read -r line`. The PID at index [1] is the opencode process. But if `cat` fails (e.g., prompt file disappears), the pipeline still runs opencode with exit 0 from cat. This is fragile.
   - File: `tools/auto-run-agents.sh:505-517`
   - Risk: Exit codes may be misreported; crashed agents may not be marked failed.

### MEDIUM PRIORITY

4. **ScanOrchestratorService: CronExpression.GetNextOccurrence may return null silently (Program.cs:113, 130, 154, 176, 177, 196)**
   - `CronExpression.GetNextOccurrence` returns `DateTimeOffset?`. In `ProcessScheduledScanAsync` (line 176) and `EfScanSchedulerStore.CreateAsync` (line 196), this value is assigned to `NextRunAt` which is `DateTimeOffset?`. The method iterates up to 366*2 iterations but can return `null` if parsing fails. No null-check is performed before assignment. Downstream code that reads `NextRunAt` (e.g., in the scheduled scan query at line 165) could get null, causing tasks to be considered "always due" (line 165: `!s.NextRunAt.HasValue || s.NextRunAt <= now`).
   - File: `src/Services/Argus.ScanOrchestratorService/Program.cs:113-130, 165, 176-177, 196`
   - Risk: Scheduled scans with invalid cron expressions could cause infinite reprocessing loops.

5. **ArgusWorkerBackgroundService: SemaphoreSlim initialized with MaxConcurrency then released before first task (lines 36-51, 53-74)**
   - At line 26, `_concurrencyLimiter = new SemaphoreSlim(worker.Capability.MaxConcurrency, worker.Capability.MaxConcurrency)`. In `ExecuteAsync`, the semaphore is waited on (line 36), then `RunTaskWithReleaseAsync` is called asynchronously without await (line 37 `_ = RunTaskWithReleaseAsync(stoppingToken)`). The semaphore is released in the finally block of `RunTaskWithReleaseAsync` (line 72). But `_concurrencyLimiter.CurrentCount` at line 57 reports `- _concurrencyLimiter.CurrentCount` which equals `MaxConcurrency - CurrentCount` where `CurrentCount` is the number of available slots. If `MaxConcurrency` is 5 and 1 slot is taken, `CurrentCount` is 4, so `5-4=1`. However, after the first `WaitAsync` succeeds, the count is 4. But the task fires and releases immediately, so multiple concurrent `RunTaskWithReleaseAsync` calls could all compute `runningTasks` before any releases happen.
   - File: `src/BuildingBlocks/Argus.BuildingBlocks.Workers/ArgusWorkerBackgroundService.cs:26, 36-51, 53-74, 57`
   - Risk: Heartbeat reports incorrect running task count; bug #14 fix may not fully address the symptom if the concurrency model doesn't account for the fire-and-forget pattern.

6. **Review-agents.sh: Reviewer state not persisted atomically; concurrent writes possible (lines 55-63, 105-114)**
   - `write_reviewer_state()` writes to a temp file then renames. This is atomic. But `spawn_reviewer()` updates the reviewer's state to "reviewing" inside a subshell `(&)`, then the parent continues. The subshell's state writes are visible to the parent via the file (since they share the filesystem). This is safe for single reviewer. However, both reviewer-1 and reviewer-2 could theoretically spawn simultaneously on the same batch if both have idle/crashed status. This is intentional per `run_once()` logic. No mutex prevents concurrent writes to the same reviewer state file if one reviewer is slow and the other's `read_reviewer_state()` races between read and write.
   - File: `tools/review-agents.sh:55-63, 105-114, 262-297`
   - Risk: Low - the file rename is atomic; the window for a corrupted state file is very small.

7. **agent-coord.sh: `write_state` no longer commits to git unless AGENT_COORD_AUTOCOMMIT=1 (ef75e3ea lines 42-55)**
   - The git auto-commit behavior was made conditional on `AGENT_COORD_AUTOCOMMIT`. Without this env var set, the agent task state file changes are not committed or pushed. This means the coordination state is not replicated across clones. This is a significant operational change: if multiple workers run with different clones, their state files will diverge and `reconcile_task_board()` may produce unexpected results.
   - File: `tools/agent-coord.sh:42-55`
   - Risk: Coordination state drift across distributed workers; task board may become inconsistent.

## Open Questions

1. **Is the AGENT_COORD_AUTOCOMMIT=0 default intentional for production?** If so, how do multiple supervisor instances coordinate without git-pushed state? The `reconcile_task_board()` reads from local state file only. Distributed supervisors could have divergent views of the task board.

2. **Why was the agent self-recovery (resume from crashed) removed from `run_agent_if_needed()`?** The commit message for `5ebef78c367084de7854520c020a8121c58a37df` says "Harden agent todo supervisor loop" but removing crash-recovery seems to weaken resilience. Was the reconcile loop intended to fully replace this?

3. **Bug #14 fix (cc93e586): The heartbeat now reports `MaxConcurrency - _concurrencyLimiter.CurrentCount`. Does this account for the fire-and-forget pattern where multiple `RunTaskWithReleaseAsync` calls may be in flight simultaneously?** The semaphore count fluctuates between wait and release. The `runningTasks` value at line 57 is snapshot; it could be 0 even when tasks are running if all are between the `WaitAsync` and the `Release`.

4. **review-agents.sh: Is the RECENT_LIMIT of 20 appropriate for the reviewer batch?** If many commits accumulate between reviewer cycles, the batch could grow large. The reviewer could spend excessive time reviewing already-reviewed commits (though the marker file prevents re-review of the same batch, new commits in the same session would add to the batch).
